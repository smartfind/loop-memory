## Window summary

This week the agent-memory ecosystem is being driven by three
competing theses, each with strong concrete signal:

1. **Git as the memory substrate.** Rune (thecolourfoundation)
   launched on Hacker News on 2026-09-25 and immediately argued
   that git's content-addressable, content-mergeable store IS the
   long-term memory layer for agents — and that putting memory in
   a separate vector DB or KV store is a category error. The
   OKF Agent Memory project has a parallel active thread (Issues
   #12-#15, 2026-09-22 → 2026-09-25) debating whether the OKF
   bundle directory should be stored as a literal git tree so any
   OKF tool can `git pull`/`git push` it. Deja-Vu (HN front-page
   2026-09-24) takes the same thesis but with SSH-synced plain
   text files and deterministic text-based search over embeddings.
   Implication for Loop Memory: the **portability** story we
   already invest in with `export-okf` is the right axis, but
   the read direction (`import-okf`) is now visibly the gap that
   every portability-focused user is going to file.

2. **Reliability of the persistent layer.** Hermes Agent merged
   460 PRs in 3 days for the v2026.9.24 release, with multiple
   PRs explicitly closing "long-lived processes stop leaking
   duplicate `state.db` writer handles". `memory-eternal` shipped
   a Windows-specific SQLite `EBUSY` fix this week and a
   `enforceAudit()` guard that installs SQLite triggers at boot
   so the `audit_log` table cannot be skipped even if a writer
   bypasses the Python wrapper. Memori shipped a v0.9.27 → v0.9.29
   "deprecation fix" that re-routed the entire consolidation path
   off an `asyncio.iscoroutinefunction` shim. Implication for Loop
   Memory: our existing `_safe_resolve_path()` (0.4.10) +
   `busy_timeout=5000` + `/api/healthz` + `/api/readyz` (0.4.11)
   are the right baseline, but the **audit_log write path is
   still a Python-level invariant** — a direct SQL writer can
   skip it. The `memory-eternal` pattern (DB-level triggers)
   closes that gap.

3. **Consolidation as a learned, recurring act.** Four
   academic papers this week converged on the same lesson:
   consolidation is most cost-effective when triggered by
   **recurrence** (RecMem, ACL2026 Findings), reconstructed on
   demand rather than retrieved (MRAgent), organized as a
   hierarchy of abstractions (xMemory), and structured as
   episodic → semantic transitions that preserve identity
   (Episodic-to-Semantic w/o Identity Drift). Implication for
   Loop Memory: our `cognitive-sleep --apply --stale-days` is
   time-driven; the recurrence-driven trigger is the natural
   next step, but it requires a counter on every recall hit,
   which is a bigger lift than two features allow. **Deferred
   this cycle** — track for 0.4.13 / 0.5.0.

The week's **two material findings** for Loop Memory:

- **OKF bundle `import-okf` as the symmetric counterpart to
  `export-okf`.**  The portability gap is now visibly the most
  filed gap in the Git-native thread (OKF Agent Memory #12-#15)
  and the Git-as-memory thesis (Rune, Deja-Vu). Adding
  `MemoryStore.import_okf(in_dir, scope=...)` plus a CLI flag and
  an HTTP route closes the loop. The work is bounded — an OKF
  bundle is `index.md` + N `.md` files, and our wiki table has
  all the columns we need (title/summary/body/tags/updated_at/
  source) plus an idempotent upsert path keyed on concept-id.
  Lift: ~120 LOC + 15-20 tests.

- **DB-level `audit_log` enforcement via SQLite triggers.**
  Today, an audit entry is written from `memory_store.py`'s
  Python helpers. If a process opens the SQLite file with the
  sqlite3 stdlib module directly, `audit_log` is silently
  skipped. `memory-eternal`'s `enforceAudit()` pattern installs
  SQLite triggers at migration time so every INSERT/UPDATE/
  DELETE on `memories`, `wiki_pages`, `relations`, and
  `consolidations` automatically writes an `audit_log` row in
  the same transaction. The Python-level write is kept (so the
  `actor` field still gets populated from the caller context),
  but the DB-level trigger is the floor — even a raw SQL writer
  cannot bypass it. Lift: ~40 LOC + 8-10 tests.

Both patterns are **stdlib-only** (no new third-party deps).

## Material findings

### 1. OKF v0.2 `import-okf` — closing the portability loop (2026-09-22 / 2026-09-25)

- **Source.** `okf-memory/okf-agent-memory` Issues #12-#15
  (2026-09-22 → 2026-09-25) + `thecolourfoundation/rune` HN
  launch (2026-09-25) + `Deja-Vu` HN front-page (2026-09-24) +
  Google OKF v0.2 spec (Apache-2.0, 2026-09-01).
- **License.** Apache-2.0 (OKF spec). MIT (Rune, Deja-Vu,
  okf-agent-memory).
- **Highlights.**
  - OKF Agent Memory Issue #14 (2026-09-22): "How do I migrate
    my existing Loop Memory bundle into OKF Agent Memory?"
    → confirms that the read direction is the most-filed gap.
  - OKF Agent Memory Issue #15 (2026-09-25): "Should the
    bundle live in a git tree so any OKF tool can `git pull`?"
    → confirms the Git-as-memory thesis.
  - Rune's README (2026-09-25): "git IS the long-term memory
    layer. Branches are sessions, commits are observations,
    merges are consolidations."  Implication: every OKF
    consumer is going to want a one-line ingest into Loop
    Memory.
  - Deja-Vu (2026-09-24): local-first, SSH-synced plain-text
    files, deterministic text-based search (BM25 + trigram)
    over embeddings — confirms the read direction is a
    user-visible feature, not a backport.
  - Specs we depend on (already shipped 0.4.9):
    - One concept per `.md` file; file path = concept ID
      (slug of the title).
    - `index.md` declares `okf_version: "0.2"`.
    - YAML frontmatter: `type` (required) + `title`,
      `description`, `resource`, `tags`, `generated: {by, at}`,
      `sources: [...]`, `stale_after`.
    - Consumers MUST tolerate unknown keys.
- **Adoption this cycle.** **The `import-okf` pattern is
  adopted.** `MemoryStore.import_okf(in_dir, scope=...)` walks
  an OKF bundle, parses `index.md`, then for each child `.md`
  file:
    1. Slug-of-title is the concept ID; if the file already
       exists for `(scope, slug)` we **upsert** (update title /
       summary / body / tags / `updated_at`), not duplicate.
    2. `generated.at` (ISO 8601) → `wiki_pages.updated_at`
       (epoch int). If `generated.at` is missing, fall back to
       the file's mtime.
    3. `tags` (JSON array of strings) → `wiki_pages.tags`
       (JSON array of strings). Missing or non-array → `[]`.
    4. `sources` → recorded as a JSON list on the wiki row
       (`sources` column already exists; was set to `[]` by
       default).
    5. Body below frontmatter → `wiki_pages.body` verbatim.
    6. Scope: CLI/HTTP callers must pass an explicit scope;
       the OKF bundle's `index.md` may declare a `scope:`
       frontmatter key (extension field, spec-safe) which is
       honoured, but defaults are conservative.
  CLI: `loop-memory import-okf <in_dir> [--scope SCOPE]
  [--dry-run] [--skip-conflicts]`. HTTP:
  `POST /api/import/okf` accepting `{in_dir, scope?, dry_run?,
  skip_conflicts?}` and returning a summary dict
  `{imported, updated, skipped, errors: [{path, reason}]}`.
  The path-safety guard from 0.4.10
  (`_safe_resolve_path()` in `loop_memory/serve/routes/_shared.py`)
  is reused unchanged.
- **Why this one.** The read direction is the single most
  visible gap this week (OKF #14, Rune, Deja-Vu all converge on
  it). Our `export-okf` from 0.4.9 makes the bundle but the
  user has nowhere to bring a bundle back into Loop Memory
  without manual re-authoring. With `import-okf`, a Loop Memory
  user can ingest an OKF bundle from `ai-memory`,
  `okf-agent-memory`, Rune, or any OKF-native tool. This is
  the case where **closing what we've already shipped** has
  higher leverage than picking up a brand-new pattern.
- **What we explicitly do NOT lift.** "Native mode" (every wiki
  page IS an OKF file on disk) — same deferral as 0.4.9.
  Git-tree storage of the bundle — same deferral; the OS
  filesystem is sufficient today. Auto-detection of OKF bundles
  by walking a user-supplied dir tree looking for an `index.md`
  with `okf_version` — deferred; the user must point us at the
  bundle root explicitly.
- **Source attribution.** `thecolourfoundation/rune` HN launch,
  MIT, 2026-09-25; `okf-memory/okf-agent-memory` Issues #12-#15,
  MIT, 2026-09-22 → 2026-09-25; `Deja-Vu` HN launch, MIT,
  2026-09-24; Google OKF v0.2 spec, Apache-2.0, 2026-09-01.

### 2. memory-eternal `enforceAudit()` — DB-level audit triggers (2026-09-23)

- **Source.** `cogstate-eng/memory-eternal` README + Release
  notes for v0.4.3 (2026-09-23).
- **License.** MIT.
- **Highlights.**
  - At migration time, install SQLite triggers:
    `trg_memories_ai`, `trg_memories_au`, `trg_memories_ad`,
    `trg_wiki_pages_ai`, `trg_wiki_pages_au`,
    `trg_wiki_pages_ad`, `trg_relations_ai`,
    `trg_relations_au`, `trg_relations_ad`,
    `trg_consolidations_ai`, `trg_consolidations_au`,
    `trg_consolidations_ad`. Each inserts into `audit_log`
    with `actor='db_trigger'`, `op='INSERT'|'UPDATE'|'DELETE'`,
    `entity=<table>`, `entity_id=NEW.id` (or `OLD.id` for
    DELETE), `at=<unix_ts>`.
  - The Python-level audit write is kept (so `actor` carries
    caller context) but the DB trigger is the **floor**: a
    direct sqlite3 writer that bypasses the Python wrapper
    still cannot skip the audit row.
  - Adds a one-time migration step (`SCHEMA_VERSION` bumps
    `0.2` → `0.3` with a forward-only `ALTER` of triggers).
- **Adoption this cycle.** **The DB-level `audit_log`
  enforcement pattern is adopted.**
  `MemoryStore._install_audit_triggers()` runs once on
  `__init__` after the schema migration, idempotent on
  re-open. The triggers are installed via `CREATE TRIGGER IF
  NOT EXISTS ...`. The Python-level `audit_log` writes in
  `memory_store.py` are kept (so the `actor` field still
  reflects caller context, e.g. `loop-memory CLI`, `serve`),
  but if the caller bypasses the wrapper, the DB trigger
  ensures an audit row with `actor='db_trigger'` is written.
  Tests cover both paths: a CLI write produces
  `actor='loop-memory CLI'`; a raw `sqlite3` write produces
  `actor='db_trigger'`.
- **Why this one.** Today's audit_log write is a Python
  invariant, not a database invariant. A misbehaving writer
  (or a malicious one) can `UPDATE memories SET body=...`
  directly and leave no audit trail. The trigger pattern
  turns "did we remember to call the audit helper?" into a
  structural property of the database.
- **What we explicitly do NOT lift.** Per-row HMAC chain
  (memory-eternal also signs each audit row for tamper
  evidence) — needs a secret-management story we don't have
  in the public-CLI surface. Track for the next cycle when
  we revisit auth.
- **Source attribution.** `cogstate-eng/memory-eternal`
  v0.4.3, MIT, 2026-09-23.
