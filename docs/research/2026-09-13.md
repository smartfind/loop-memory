## Window summary

The week's strongest concrete signal is **tigerless-labs/agent-memory
v0.3.0 (2026-09-08)**, which formalises the **L0 / L1 / L2 / L3
recall ladder**: `recall()` returns only an L0 list (`id`, `kind`,
`abstract`, `score`, `why`) — agents open what they want at the depth
they need. Today our `recall()` returns the full text of every hit, so
an agent that only needs to identify the top three candidates wastes
tokens reading multi-KB hits it will then ignore. The lift is small
(≤ 60 LOC) and the win for agent-loop workflows is large.

The runner-up is the **Mem0 CLI `mem0 init --agent <name>` pattern
(2026-09-07)**: agents mint their own working config + identity in
under five seconds. We already ship `install-hooks`, but we don't
track *which* agents are registered or which ones last touched the
store. The lift is an `agents` table plus a new `loop-memory init
--agent <name>` command that bundles `install-hooks` + identity
registration in one call.

`rohitg00/agentmemory v0.9.0 (2026-09-09)` exposes its RRF fusion as
a debug field on every recall hit (`recall_fusion_debug`). We already
fuse BM25 + embeddings inside `recall_hybrid()`; surfacing the per-
signal contributions (which the existing `why: [...]` provenance list
already approximates) would let the dashboard show "0.4 BM25 + 0.3
embedding + 0.2 short_query_boost" without a new DB column.

## Material findings

### 1. tigerless-labs/agent-memory v0.3.0 — L0/L1/L2/L3 recall ladder (2026-09-08)

- **Source.** Release notes + `recall.py` source for
  `tigerless-labs/agent-memory v0.3.0` (2026-09-08).
- **License.** MIT.
- **Highlights.**
  - `recall()` returns L0 only: `{id, kind, abstract, score, why}`.
  - `recall_l1(id)` returns the full text body.
  - `recall_l2(id)` returns the body plus source provenance.
  - `recall_l3(id)` returns the body plus the full audit trail.
  - The L0 abstract is at most 80 chars and is computed at index
    time, so `recall()` is a pure projection (no join, no body read).
- **Adoption this cycle.** **The L0 path-list pattern is adopted.**
  `MemoryStore` gains a `recall_paths(query, limit=12, include=...)`
  method that returns the same ranked lists as `recall()` but each
  hit's `text` / `body` is replaced with a short `abstract` (≤ 80
  chars), and `body` / `preview` are dropped entirely. CLI surface:
  - `loop-memory recall-paths <query>` (new subcommand).
  - `loop-memory recall <query> --outline` (new flag).
  HTTP route: `GET /api/recall/outline?q=…&limit=…`.
- **Why this one.** Today an agent that calls `GET /api/recall?q=…`
  pays for the full text of every hit. For a typical query this is
  5-15 KB of body text per hit, and the agent usually picks the top
  three — meaning 60-80 % of the bytes are thrown away after the
  first read. Returning only `{id, kind, abstract, score, why}` cuts
  the payload by 10× and lets the agent open the L1 body only for
  the candidates it actually wants.
- **What we explicitly do NOT lift.** A separate `recall_l1/l2/l3`
  API for the body fetch — we already have `GET /api/memories/{id}`
  for that. The ladder is a recall-side affordance, not a new body
  API.
- **Source attribution.** `tigerless-labs/agent-memory v0.3.0`,
  2026-09-08, MIT.

### 2. Mem0 CLI `mem0 init --agent` — per-agent identity bootstrap (2026-09-07)

- **Source.** PR #4128 + `mem0/cli/init.py` source for
  `mem0ai/mem0` (2026-09-07).
- **License.** Apache-2.0.
- **Highlights.**
  - `mem0 init --agent <name>` writes a per-agent config dir
    (`~/.mem0/agents/<name>/config.yaml`), registers the agent in a
    local `agents.json` index, and prints a one-line summary so the
    agent can verify its setup.
  - The local index tracks `name`, `scope`, `created_at`,
    `last_seen_at`, and `hooks_installed`.
  - Re-running with the same name is idempotent — it bumps
    `last_seen_at` and reports the existing config dir.
- **Adoption this cycle.** **The per-agent identity bootstrap pattern
  is adopted.** New `agents` table:
  `agents(name TEXT PRIMARY KEY, scope TEXT NOT NULL DEFAULT 'global',
  created_at REAL NOT NULL, last_seen_at REAL NOT NULL,
  hooks_installed INTEGER NOT NULL DEFAULT 0)`.
  New `MemoryStore` methods: `register_agent(name, scope='global') ->
  dict` and `list_agents() -> list[dict]`. New CLI surface:
  `loop-memory init --agent <name>` (registers + optionally runs
  `install-hooks` and prints a one-line summary).
  `install-hooks` is also extended so each call bumps
  `last_seen_at` on every agent it touches.
  `SCHEMA_VERSION` bumps "9" → "10".
- **Why this one.** Today `install-hooks` knows it ran, but the store
  has no record of *which* agent it ran for. When a user files an
  issue like "my Codex install is not seeing my Claude memories", the
  first diagnostic question is "which agents are registered, and when
  did they last touch the store?" — today the answer is "open
  `~/.loop_memory/agents.json` if it exists, otherwise grep your
  bash history". The new table makes that one SQL query away.
- **What we explicitly do NOT lift.** A full per-agent config dir
  (`config.yaml` + secrets) — that's a hosting-side concern and
  overlaps with whatever the user's CLI client already stores. We
  only need the *index*, not the per-agent secrets.
- **Source attribution.** `mem0ai/mem0` PR #4128, 2026-09-07,
  Apache-2.0.

### 3. rohitg00/agentmemory v0.9.0 — `recall_fusion_debug` field (2026-09-09)

- **Source.** Release notes + `recall_hybrid.py` source for
  `rohitg00/agentmemory v0.9.0` (2026-09-09).
- **License.** MIT.
- **Highlights.**
  - Every recall hit now carries `recall_fusion_debug: {"bm25": 0.42,
    "embedding": 0.31, "short_query_boost": 0.19}` so the dashboard
    can render a stacked-bar "what contributed to this score" widget.
  - The numbers sum to ~1.0 (normalised), so the widget doesn't need
    a separate scale.
- **Adoption this cycle.** **Deferred — already implicit in our
  `why: [...]` provenance list.** Our `recall()` already produces a
  discrete label list (`keyword_match`, `tag_match`, `high_importance`,
  `high_score_field`, `short_query_boost`, `high_recall_count`); the
  numeric equivalent would require either recomputing the score
  decomposition inside the store or storing it as a new column.
  Track for next cycle once we have a concrete dashboard widget
  request.
- **What we explicitly do NOT lift.** The numeric score decomposition
  this cycle; the discrete label list is sufficient today.
