## Window summary

The week's biggest concrete signal is **Mem0 v2.0.19 (2026-08-25)**, which
ships the public rollout of the **"Dream"** background-consolidation loop:
when the daily cron fires, the consolidator walks every memory in a
project namespace, identifies clusters of **near-duplicates** (cosine
sim ≥ 0.95), **outdated facts** (older snapshot with lower importance and
superseding claim), and **stale hot memories** (high recall_count but
very low importance), and writes **explicit supersession pointers**
(`memory.superseded_by = <winner_id>`) rather than silent DELETE. The
pattern is exactly the audit-trail our current `merge_memories()` lacks
(it currently DELETEs the loser with no trace). This cycle adopts a
slimmed-down version of the pattern.

The rest of the window: **MemOS v1.0.0-M10** landed (more about the new
plugin pipeline than memory semantics; defer), **agentmemory v1.2.0**
shipped a small **recall provenance / keyless graph / connector parity**
set (defer the connector work, lift the provenance shape), and two
newcomers appeared (**Telemem** as a high-perf Mem0 drop-in; **Compartment**
as an encrypted fully-offline memory map). TencentDB stayed silent after
their 2026-08-13 "Team Memory" addition — still on the watchlist.

Three new peer projects crossed the radar this cycle:

- **`agentmemory`** (`nagyist/agentmemory`, MIT, ~250 stars) shipped
  `v1.2.0` on 2026-08-25. Their **recall provenance labels** — every
  recall hit returns a small `why: [...]` array naming which signals
  matched (keyword / tag / recency / importance / graph) — are the
  liftable item (§2 below). They also shipped a `recall_count`
  cap-and-decay shape and a "keyless graph" mode; both are defer
  for now (cap-and-decay is already implicit in our
  `temporal_score`; keyless graph is mostly their deployment
  compromise).
- **`CodeAbra/iai-personal-memory-engine`** (MIT) pushed
  `v0.5.0` on 2026-08-27. Cross-agent MCP server aimed at
  Cursor / Claude / Codex / OpenClaw / Hermes. Architecture
  overlap is high (also a single-user, local-first SQLite
  store, also an MCP server); the README is the most useful
  artefact this cycle and worth keeping on the watchlist.
  No code lift — body too small and the design is mostly
  composable from primitives we already have.
- **`MaxFreedomPollard/Compartment`** (Apache-2.0, 2026-08-28).
  Encrypted fully-offline agentic memory with a memory-map GUI.

## Material findings

### 1. Mem0 v2.0.19 — Dream supersession chain (2026-08-25)

- **Source.** Release notes for `mem0ai/mem0 v2.0.19` (2026-08-25),
  cross-referenced with the open PR thread on
  `mem0ai/mem0#dream-loop-v2`.
- **License.** Apache-2.0.
- **Highlights.**
  - **Background "Dream" consolidation** runs weekly per
    project namespace, walking every memory in batches of 256
    so the cron cost is bounded.
  - Near-duplicate clusters (cosine sim ≥ 0.95) are folded
    into a single "winner" memory, with each loser receiving
    an **explicit `superseded_by` pointer** to the winner.
    The pointer is a real column, not a tag — `recall()` skips
    superseded rows in O(1) via a partial index.
  - Outdated facts (older snapshot, lower importance, newer
    replacement present) also receive a pointer rather than
    being deleted.
  - The audit trail is queryable: `GET /v1/memories/{id}/history`
    walks the chain and returns the full evolution.
- **Adoption this cycle.** **The supersession-pointer
  pattern is adopted.** `MemoryStore` gains:
  - `superseded_by TEXT` column on `memories`
    (nullable FK to `memories.id`, `SCHEMA_VERSION` bumped
    "8" → "9").
  - `merge_memories()` now writes a `superseded_by` pointer
    on the loser instead of `DELETE FROM memories` — the
    audit row stays around for the history chain.
  - `recall()` filters `superseded_by IS NULL` so callers
    see the latest view.
  - `list_superseded(superseded_by=None) -> list[dict]`
    enumerates the chain.
  - `trace_supersession(target_id) -> list[str]` walks the
    full ancestry.
  - CLI surface: `loop-memory audit supersede` and
    `loop-memory audit supersede --target <id>` (the latter
    prints the ancestry chain).
- **Why this one.** Our current `merge_memories()` already
  inserts into `contradiction_ignored` (a separate suppression
  table) but **deletes the loser's row**, which means a
  user auditing the store a month later has no way to see
  "memory X was merged into memory Y on date Z". The
  Mem0 pointer pattern makes the chain auditable without
  paying for it in the hot recall path.
- **What we explicitly do NOT lift.** Mem0's full Dream
  loop (weekly cron, near-dup clustering, importance
  re-bucketing) is too large for this release. Our
  `cognitive-sleep` already does the cheap-and-deterministic
  equivalent on demand; the chain-pointer work is what
  makes it auditable.

### 2. agentmemory v1.2.0 — recall provenance labels (2026-08-25)

- **Source.** Release notes + README diff for
  `nagyist/agentmemory v1.2.0` (2026-08-25).
- **License.** MIT.
- **Highlights.**
  - Every `recall()` response carries a small `why: [...]`
    array per hit. Labels include `keyword_match`,
    `tag_match`, `recency`, `high_recall_count`,
    `high_importance`, `graph_neighbor`, `short_query_boost`.
  - The labels are surfaced through the CLI with a `--verbose`
    flag and through the dashboard as a tooltip on each hit.
  - The whole shape fits in ~30 lines of code and zero
    new dependencies.
- **Adoption this cycle.** **The provenance-label pattern
  is adopted.** `MemoryStore.recall()` populates
  `why: [...]` per memory hit using the same labels
  agentmemory uses (the specific labels are slightly
  trimmed to match our scoring arithmetic). CLI:
  `loop-memory recall --verbose` prints each hit's
  provenance alongside the existing fields. The
  dashboard's recall panel can pick the same field up
  via the existing `GET /api/recall` route.
- **Why this one.** Today a user staring at a recall
  hit that "shouldn't" be there has no way to ask
  "why did this surface?" except by reading our recall
  code. The provenance label makes the answer obvious
  from the CLI itself. Cheap, isolated, no deps.
