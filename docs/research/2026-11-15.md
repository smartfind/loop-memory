## Headline

The window was dominated by one theme: **projects stopped sharing one
flat memory pool and started giving each caller its own slice.**

* `plastic-labs/honcho` v3.6.0 shipped multi-tenancy — `tenant_id`
  now leads every primary key and every read and write is scoped by
  the caller's JWT.
* `EverMind-AI/EverOS` v1.6.0 made deletion owner-scoped and refused
  to delete half of a session (`503 SESSION_BUSY`).
* `thedotmack/claude-mem` made "each scope gets its own project by
  default", and made "an explicitly empty project selection show
  nothing instead of observations from every project" (#5866).
* `vectorize-io/hindsight` stopped a bank clone from taking over
  another bank's alias (#6280).

Reading those against Loop Memory's own code turned up a real defect:
**Loop Memory's agent-namespace filter had never worked.** The release
that came out of this audit is **0.4.22 — namespace isolation, with
the predicate pushed into the SQL** (`docs/namespace-isolation.md`).

## Decisions

### ADOPT — namespace isolation, enforced in SQL (shipped in 0.4.22)

**What.** `MemoryStore.recall()` / `recall_hybrid()` / `recall_as_of()`
now take `agent_id` / `user_id` and apply the predicate inside the
SQL. Every retrieval channel (BM25, semantic, entity) carries it.
`/api/v1/recall`, `/api/recall`, the MCP `recall` tool, the SDK
clients and `loop-memory recall` all expose it.

**Why.** Reading the window against Loop Memory's own code found that
the namespace filter **had never worked**:

* on the legacy path it was a **silent no-op** — `MemoryStore.recall()`
  never returned `agent_id` / `user_id`, so the route's predicate read
  `None`/`None` for every row and let every row through. An agent
  that explicitly asked for its own namespace was handed **every other
  agent's memories**;
* on the hybrid path it ran **after** the `LIMIT`, so a foreign
  namespace could spend the caller's whole result budget and the
  caller could get zero hits while its own rows sat further down.

Both are the same root cause: the predicate was in the caller instead
of in the query. `honcho` v3.6.0 made `tenant_id` lead every primary
key with row-level security on every read and write; `EverOS` v1.6.0
made deletion owner-scoped; `claude-mem` gave each scope its own
project by default. The pattern is the same in all three — **scope the
query, not the result.**

Full contract: `docs/namespace-isolation.md`.
43 new regression cases; suite at **1084 passed / 4 skipped**.

### DEFER — the `pending` list (EverOS v1.7.0)

> "information seen only once waits here until a later conversation
> confirms it, which cuts down on wrong entries"

A confidence-gated promotion: a fact seen exactly once is provisional
and only becomes durable after corroboration. Loop Memory already has
the pieces (`importance`, `valid_at` / `invalid_at`, the supersession
chain) but not the *observation count* that would drive the gate.

**Why deferred.** It needs a new "how many times have we seen this"
counter, which means a schema migration and a second write path. It
is a good candidate for 0.4.23 — it is the single most interesting
idea in this window's releases.

### DEFER — the destructive-operation audit (hindsight #5961, 2026-11-03)

> "always log destructive operations and name the tool in MCP call logs"

Loop Memory has an `audit_log` table but the MCP delete tools do not
name themselves in it. EverOS v1.7.0's `purge` → `purge/confirm` →
progress shape is also worth copying: a destructive operation that
needs a second, explicit confirmation.

**Why deferred.** Two changes, not one; the purge API in particular
needs a job table and a progress surface.

### DEFER — MCP destructive-operation tooling in general

`rohitg00/agentmemory` v0.9.33 added `memory_diagnose` / `memory_heal`
to find and remove *orphaned* records — a maintenance surface rather
than a blind delete. Worth adopting once the audit log names the tool.

### DEFER — bounded listing offsets (claude-mem #6083, agentmemory #1636)

> "Worker listing endpoints stop at offset 10,000" · "Unpaged
> `GET /memories` and `/relations` over the transport limit return 413
> with a paging hint"

Loop Memory's `/api/v1/memories` already caps `limit` at 500 and the
timeline uses cursor pagination, so there is no deep-offset hole
today. But the **413-with-a-paging-hint** contract for an unpaged
request over the transport limit is a good API convention to copy.

### REJECT — importing honcho's or OpenViking's code

Both are **AGPL-3.0**. Loop Memory is MIT. Only the *pattern* was
taken (scope the query; refuse to hand out an empty namespace). No
code was copied, no API was mirrored.

### REJECT — `vercel/ai` / `langchain` / `mastra` release churn

30 and 7 releases respectively in the window, all dependency bumps
with no change to any memory surface. Not worth the research budget.

  0.4.23 — a fact seen once is provisional until it is confirmed.

  distilled *profile* view does not exist yet. That is a natural
  companion to the `pending` list.

  writes before they are stored") is a human-review gate — probably
  too big for one release, but the shape is worth remembering.

  worth checking against Loop Memory's own ordering. Loop Memory
  redacts before embedding in the ingest pipeline, so it is probably
