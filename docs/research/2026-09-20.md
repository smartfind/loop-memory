## Window summary

The week's strongest concrete signal is **Google's Open Knowledge Format
v0.2** — a vendor-neutral markdown + YAML-frontmatter standard for
packaging the context AI agents depend on. Two projects converged on
it this window: `akitaonrails/ai-memory 2.0` (2026-09-02) made every
wiki page a native OKF document, and `okf-memory/okf-agent-memory`
(2026-09-06) shipped a Go implementation with sub-300µs BM25 + embedded
MCP. Today Loop Memory's `MEMORY.md` export is markdown-shaped but
not OKF-conformant. The lift is small (~80 LOC) and the win is
**portability**: a user can hand an OKF bundle to any OKF-aware tool
(Grep, Obsidian, ai-memory, okf-agent-memory, the next 5 tools we
haven't seen yet) and not start over.

Runner-up is the **bi-temporal "as_of" recall** pattern that
`loomcycle` shipped across RFCs BL/BS/BU/BV/BW (v1.33 → v1.49). Each
memory row carries both `observed_at` (when it was written) and a
bi-temporal `valid_at` / `invalid_at` pair so a query like "what did
we know about X on 2026-08-01?" returns the answer that was true at
that moment, not the latest answer. We already track `created_at` /
`updated_at` on every memory and the `superseded_by` chain we shipped
in 0.4.6 lets us reconstruct `invalid_at` on demand. The lift is a
single `recall_as_of(query, as_of_ts, ...)` method + a CLI flag.

## Material findings

### 1. OKF v0.2 — the agent-memory standard that emerged this window (2026-09-01 spec)

- **Source.** Google's `okf/SPEC.md` v0.2 (verified 2026-09-01) +
  `akitaonrails/ai-memory 2.0` (2026-09-02) + `okf-memory/
  okf-agent-memory` (2026-09-06).
- **License.** Apache-2.0 (OKF spec, ai-memory). MIT (okf-agent-memory).
- **Highlights.**
  - One concept per `.md` file; file path = concept ID.
  - YAML frontmatter with `type` (required) + `title`,
    `description`, `resource`, `tags`, `generated: {by, at}`,
    `sources: [{resource, author?}]`, `stale_after`.
  - v0.2 supersedes v0.1: replaces `timestamp` with `generated.at`
    and `# Citations` body section with `sources` frontmatter.
  - An OKF bundle is a directory + an `index.md` declaring
    `okf_version: "0.2"`.
  - Consumers MUST tolerate unknown keys (extension fields are
    spec-safe).
  - `okf-skills` is the toolchain; ships as a Claude Code plugin
    and via `skills.sh` to 20+ platforms.
- **Adoption this cycle.** **The OKF v0.2 export pattern is
  adopted.** `MemoryStore.export_okf(out_dir, scope_filter?)` writes
  an OKF bundle: one `.md` file per wiki page (the concept ID is the
  slug), an `index.md` with `okf_version: "0.2"`, and a
  deterministic frontmatter mapping:
    - `type`: derived from the page's `kind`/`scope` (wiki → "Note"
      by default; explicit `kind` frontmatter on the source wins).
    - `title`: `wiki_pages.title`.
    - `description`: `wiki_pages.summary` (when present).
    - `tags`: `wiki_pages.tags` (JSON array).
    - `generated.at`: `wiki_pages.updated_at` (ISO 8601).
    - `generated.by`: `wiki_pages.source` or "loop-memory" when no
      source is recorded.
  CLI: `loop-memory export-okf <out_dir> [--scope SCOPE]`.
  HTTP: `POST /api/export/okf` accepting `{out_dir, scope?}` and
  returning a summary dict. Mem0 memories are NOT exported to OKF
  this cycle — only wiki pages, which are the durable, human-curated
  concepts OKF is designed for. Raw memories already have a
  separate `export-bundle` path.
- **Why this one.** A user who runs Loop Memory today and then
  switches to ai-memory or okf-agent-memory loses the wiki content;
  a user who runs OKF-native tools and wants to try Loop Memory
  can't bring their bundle in without manual re-authoring. An
  `export-okf` closes the loop on the export side; `import-okf`
  lands in a future cycle once we need to validate against real
  bundles.
- **What we explicitly do NOT lift.** Full "native" mode (every wiki
  page IS an OKF file on disk). That's a schema/storage rewrite
  with a real migration cost; the export path gives users 90 % of
  the value at 10 % of the risk. Defer until a user files a request.
- **Source attribution.** `akitaonrails/ai-memory 2.0`, MIT,
  2026-09-02; `okf-memory/okf-agent-memory`, MIT, 2026-09-06;
  Google OKF v0.2 spec, Apache-2.0, 2026-09-01.

### 2. loomcycle v1.33+ — bi-temporal `as_of` recall (2026-09-15)

- **Source.** `loomcycle.dev` (RFC BL + BS + BU + BV + BW) +
  `loomcycle/memory-view` README.
- **License.** Apache-2.0.
- **Highlights.**
  - Every memory row carries an `observed_at` (when said) and a
    bi-temporal `valid_at` / `invalid_at` (when true), so a query
    can ask "what was true at moment T" rather than only "what is
    true now".
  - The retrieval API surfaces an `as_of` parameter; results are
    filtered to rows where `observed_at <= as_of` AND
    (`valid_at IS NULL` OR `valid_at <= as_of`) AND
    (`invalid_at IS NULL` OR `invalid_at > as_of`).
  - Each row is labelled with its source class — "fact a
    consolidator distilled", "note an agent wrote", or "document
    prose" — so the agent (and the dashboard tooltip) can tell
    provenance at a glance.
- **Adoption this cycle.** **The `as_of` recall pattern is adopted.**
  `MemoryStore.recall_as_of(query, as_of_ts, limit=12, ...)` returns
  hits that were valid at `as_of_ts` (which may be a `float` epoch
  or an ISO-8601 string the caller passes in). The implementation
  is additive: we already track `created_at` on every memory and
  the `superseded_by` chain (0.4.6) lets us compute `invalid_at`
  per row at query time. CLI:
  `loop-memory recall <query> --as-of <ISO|epoch>`. HTTP:
  `GET /api/recall?as_of=…`.
- **Why this one.** Today, when a user files "but last month Loop
  Memory was telling me X", there is no way to verify what was true
  in the store at that moment — only what is true now. `as_of`
  makes the audit conversation one CLI call instead of a SQLite
  archaeology expedition.
- **What we explicitly do NOT lift.** Full bi-temporal ingest (we'd
  have to add `valid_at` / `invalid_at` columns and rewrite
  supersession to write `invalid_at` on the loser). For now
  `as_of` derives `invalid_at` from the `superseded_by` chain at
  read time, which gives correct answers without the schema
  rewrite. Watch for the next cycle.
- **Source attribution.** `loomcycle` v1.33-v1.49, Apache-2.0,
  2026-09-15.

### 3. Accenture mercury-go agent-memory — "deterministic decay + supersession" (2026-09-10)

- **Source.** `accenture.github.io/mercury-go` + `Accenture/
  mercury-go` README.
- **License.** Apache-2.0.
- **Highlights.**
  - "Backward — Evolving Memory" is an event-sourced ledger
    projected into a live `continuity.md` with deterministic decay,
    supersession, invariant re-verification, contradiction checks,
    and provenance.
  - The supersession half overlaps with our 0.4.6 work.
  - The "deterministic decay" half is interesting: every memory
    tier has an integer-counted decay, no floating-point.
- **Adoption this cycle.** **Deferred — half already shipped, the
  other half needs a redesign.** Our `rescore` + `cognitive-sleep
  --apply --stale-days` already do floating-point decay. The
  "deterministic" half (integer-only scoring) is a behavior change
  we don't want to ship without a benchmark. Track for the 0.4.10
  / 0.5.0 cycle when we revisit scoring.

### 4. nickthelegend/loom — OpenTelemetry-exported action log (2026-09-19)

- **Source.** `github.com/nickthelegend/loom` README + Releases.
- **License.** MIT.
- **Highlights.**
  - Every turn, handoff, and route step is exported as
    OpenTelemetry traces/metrics/logs and read back into an
    in-app Observatory.
  - Pattern: `kind` enum per action (read/write/edit/grep/
    glob/notebook_edit/http/webfetch/websearch/bash/agent/skill/
    memory/recall/channel/history/path/document/agent_def/skill_def/
    evaluation/interruption/context) — 25 distinct action classes.
- **Adoption this cycle.** **Deferred — overlaps with our existing
  `audit` trail and `llm_audit` table.** Our audit trail is
  already structured; bolting OpenTelemetry exporters on top is
  ~300 LOC for marginal value. Watchlist until a user asks.

### 5. LinearMemory — pgGraph projection over PostgreSQL (2026-09-15)

- **Source.** `github.com/jucelioalencar/linearmemory` README.
- **License.** MIT.
- **Highlights.**
  - Four-tier separation: Context / Events / Reflections /
    Memories, with PostgreSQL as authoritative and a pgGraph
    projection that's rebuildable.
