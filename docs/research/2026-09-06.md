## Window summary

The week's strongest concrete signal is **Mem0 v2.0.20 (2026-09-02)**,
which ships a **semantic splitter** (long documents chunked by meaning,
not character count), **per-chunk `memory_policy`** (keep / drop), and
a **memory-explainability debug endpoint** that surfaces *why* one hit
ranked above another. The explainability endpoint is the closest shape
to last cycle's `why: [...]` provenance work — the same problem, a
different surface. The per-chunk policy is mostly relevant to
LLM-driven ingest pipelines, which we don't have yet (`defer`). The
semantic splitter is a hosting-side concern, also `defer`.

**agentmemory v1.3.0 (2026-09-03)** shipped **lifetime stats per
memory** (`remember_count`, `recall_count`, `avg_age`) plus a CLI hook
`agentmemory stats` that prints top-N most/least-used memories. This
fits cleanly into our existing `MemoryStore` (we already have
`recall_count` / `positive` / `negative` on `memory_signals`) — the
lift is a thin `MemoryStore.stats(mid) -> dict` plus a
`memory-stats <id>` CLI subcommand.

**codexa-memory v0.2.0 (2026-09-05)** landed a **portable
`.memory.sqlite`** that bundles memories + wiki + signals + audit into
a single SQLite file. Our `MEMORY.md` export is markdown-only; a
portable SQLite snapshot is a higher-fidelity sharing path and lifts
cleanly into a `MemoryStore.snapshot(out_path)` /
`restore(snapshot_path)` pair.

**LightRAG v0.4.2 (2026-09-04)** added **incremental update + cached
query** support so a re-query against an unchanged corpus returns in
O(1) instead of re-traversing the graph. Our `recall()` already caches
implicitly via the FTS mirror + signals table; the explicit
(query, corpus_fingerprint) cache is a future-cycle item.

**hypemelse/memory-mcp v0.4.0 (2026-09-05)** exposes **22 MCP tools**
including `memory_delete_older_than`, `memory_export_to_obsidian`,
`memory_import_from_json`. We already cover most of these as SDK
methods; the **MCP-tool naming convention** is the liftable item —
aligning our MCP tool names so a cross-MCP client that learned the
hypemelse vocabulary still works without a config rewrite. This cycle
adds a compatibility table to docs and defers the rename itself.

## Material findings

### 1. agentmemory v1.3.0 — per-memory lifetime stats (2026-09-03)

- **Source.** Release notes + README diff for
  `nagyist/agentmemory v1.3.0` (2026-09-03).
- **License.** MIT.
- **Highlights.**
  - `/api/v1/memories/{id}/stats` returns a small dict:
    `remember_count`, `recall_count`, `avg_age`, `last_recall_at`,
    `last_signal_at`, `positive`, `negative`.
  - CLI hook `agentmemory stats [--top N]` prints the top-N
    most/least-used memories.
  - The shape fits in ~40 lines of code and zero new dependencies.
- **Adoption this cycle.** **The per-memory lifetime-stats pattern
  is adopted.** `MemoryStore` gains a `stats(mid: str) -> dict`
  method that joins `memories` with `memory_signals` and surfaces:
  `id`, `kind`, `text` (truncated), `created_at`, `updated_at`,
  `recall_count`, `positive`, `negative`, `last_recall_at`,
  `last_signal_at`, `age_seconds`, `superseded_by`. CLI surface:
  `loop-memory memory-stats <id>`. HTTP route:
  `GET /api/memories/{id}/stats`.
- **Why this one.** We already track `recall_count`, `positive`,
  `negative` on `memory_signals`; the lift is a join + a tiny
  presentation layer. Today a user staring at a memory they think
  is "dead" has no CLI way to ask "is anyone recalling this?" —
  they have to crack open the SQLite file. The stats method makes
  the answer one CLI call away.
- **What we explicitly do NOT lift.** agentmemory's full
  `stats --top N` is a separate `top_signals()` shape we already
  have; the lift is the per-memory endpoint, not the top-N CLI.

### 2. hypemelse/memory-mcp v0.4.0 — MCP tool name alignment (2026-09-05)

- **Source.** README + tool registry for
  `hypemelse/memory-mcp v0.4.0` (2026-09-05).
- **License.** MIT.
- **Highlights.**
  - 22 MCP tools with snake_case + `memory_` prefix.
  - Cross-MCP clients (Claude Desktop, MCP-aware IDEs) have already
    learned this vocabulary, so a user moving from hypemelse to
    Loop Memory expects `memory_recall` / `memory_remember` /
    `memory_stats` etc.
- **Adoption this cycle.** **The MCP tool name alignment is
  adopted as documentation, not code** (our tool names are already
  reasonable; no rename needed this cycle). We add a small
  compatibility table to `docs/universal-agent-memory.md` listing
  which hypemelse vocabulary maps to which Loop Memory method, and
  a short note in the README's MCP section.
- **Why this one.** No code change is needed yet — the value is in
  the docs so a cross-MCP user finds the mapping without opening
  an issue.
- **What we explicitly do NOT lift.** A wholesale rename would
  break every Loop Memory MCP consumer; defer the rename until we
  see repeated requests in the issue tracker.

### 3. codexa-memory v0.2.0 — portable `.memory.sqlite` snapshot (2026-09-05)

- **Source.** README + `snapshot.py` source for
  `codexa-lab/codexa-memory v0.2.0` (2026-09-05).
- **License.** Apache-2.0.
- **Highlights.**
  - `snapshot(db_path, out_path)` writes a single SQLite file
    containing memories + wiki + signals + audit + entity_mentions.
    Schema-versioned header row so a restore can refuse a downgrade.
  - `restore(snapshot_path, target_db)` copies rows in FK order
    into the target store, upserting by primary key.
  - The shape fits in ~80 lines and uses the stdlib `sqlite3`
    module + the existing `sqlite3.Connection.backup()` API.
- **Adoption this cycle.** **The portable SQLite snapshot pattern
  is adopted.** `MemoryStore` gains two methods:
  - `snapshot(out_path) -> dict` writes a single-file SQLite
    snapshot of the live store.
  - `restore(snapshot_path) -> dict` re-hydrates a snapshot into
    the current store.
  - CLI surface: `loop-memory snapshot <out_path>` and
    `loop-memory restore <in_path>`.
  - HTTP route: `POST /api/snapshot/restore` (sister to existing
    `POST /api/import`).
- **Why this one.** Our current `export-bundle` writes a markdown
  directory that's Git-friendly but lossy (text-only, no signals,
  no entity_mentions). A portable SQLite snapshot is lossless and
  small (~1-5 MB for a typical store) — it lets a user hand their
  full store to another machine without losing the recall-quality
  signals.
- **What we explicitly do NOT lift.** The full schema-versioning
  negotiation (downgrade detection, partial restore) — out of
  scope for this cycle. A future cycle can add it.
